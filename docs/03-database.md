# Database

SQL Server database: `BillingSoftware`.

Every business table inherits the same columns:

| Column | Meaning |
| --- | --- |
| Id | Guid, generated by the API |
| CreatedAt, CreatedBy, CreatedIp | First write |
| UpdatedAt, UpdatedBy, UpdatedIp | Later writes |
| IsDeleted, DeletedAt, DeletedBy, DeletedIp | Soft delete |

EF Core global filters hide `IsDeleted = 1`. Unique indexes on restaurant code, user email, role name and module code ignore archived rows, so a code can be used again after an archive.

If any code path calls a hard delete, `SaveChanges` converts it to `IsDeleted = 1` and fills the delete stamp. There is no purge API.

## Tables in phase 1

| Table | Holds |
| --- | --- |
| Restaurants | House profile, owner phone, UPI id, active flag |
| Users | Platform and restaurant logins |
| Roles | Super admin through HR |
| UserRoles | Which roles a user has |
| Modules | The catalogue of desks |
| RestaurantModules | Whether that desk is on for one house |
| AuditLogs | Action, description, actor email, restaurant, IP, user agent |

`AuditLogs` is also soft-delete capable, but the product does not expose a delete for it. The IP for an audit row is `CreatedIp`. The API returns that value as `ipAddress`.

## Tables in phase 2

| Table | Holds |
| --- | --- |
| MenuCategories | Section of the menu, sort order, active flag |
| MenuItems | Dish, food type, price, photo path, availability |
| ItemVariants | Size or portion and its price |
| ItemAddons | Extra and its price |
| DiningTables | Name, section, seats, floor position, status, QR token |
| TableBookings | Guest, party size, start and end, status |
| GuestOrders | Token number for one India service date, table snapshot, status |
| OrderLines | Item, variant and addon snapshot, quantity, unit price |

A token number is unique per restaurant and service date among live rows. A table name and a QR token are unique among live rows of that house. Prices are stored as decimal (10,2). Guest orders stamp the guest name as the actor email when nobody is signed in.

## Tables in phase 3

| Table | Holds |
| --- | --- |
| Bills | Bill number for one India service date, tax, discount, total, cash or UPI, status |
| BillLines | Dish snapshot copied from the token |
| OwnerNotices | WhatsApp text prepared for the owner, and the `wa.me` link |

A bill number is unique per restaurant and service date among live rows. A live token can have only one bill that is not cancelled. Reports does not add a table. It reads `Bills` and `BillLines` for one service date. Cancelled bills are left out. Sales, cash, UPI, discount, and GST count only paid bills.

## Tables in phase 4

| Table | Holds |
| --- | --- |
| StockItems | Ingredient, unit, quantity on hand, reorder level |
| RecipeLines | How much of an ingredient one plate of a dish uses |
| StockMovements | Purchase, sale, or correction, with the signed quantity |

An ingredient name is unique per house among live rows. A dish can list each ingredient once. Quantities are decimal (12,3). Sale movements point at the bill that consumed them. On hand may go below zero; the bill still completes.

## Tables in phase 5

| Table | Holds |
| --- | --- |
| Shifts | Named same-day shift, start, end, grace minutes |
| ShiftAssignments | One live shift for one employee of the house |
| LeaveRequests | Casual, sick, or unpaid leave, and whether it was approved |
| AttendanceMarks | One check-in per employee per India service date, with a late flag |

A shift name is unique per house among live rows. An employee has one live shift assignment. A check-in is unique per restaurant, employee, and service date among live rows. Employees are rows in `Users` with a house role. Archiving an employee is a soft delete.

## Seed

On startup the API applies migrations and inserts roles, modules, and the super admin if that email is missing. Restarting does not reset the super admin password.
